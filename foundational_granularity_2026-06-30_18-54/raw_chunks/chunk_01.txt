The precise goal of this pipeline, how its constituent parts achieve it, and its place in the larger architecture are detailed below:

### 1. The Precise Goal
The goal of the **Deterministic Prompt and Rules Sync Pipeline** is to enforce the **Assertion-Context Boundary** by synchronizing the local filesystem master ledger (stored under `/prompts/` and `/brain/logic_packets/`) to the database indexing layers (`cove` and `amplified_brain`). This prevents any semantic drift between the code/prompt states and the active database index.

### 2. How the Constituent Chunks Achieve This
*   **Step 1: Parse and Validate (Filesystem Ledger):**
    *   *Mechanism:* Scans the directories, reads the Dual-YAML headers, asserts the presence of the 19 required metadata fields, and validates the SHA-256 hash of the content against the header's `chunk_hash_sha256`.
    *   *Result:* Rejects tampered, corrupt, or incomplete ledger files at the gate, ensuring only validated structural documents are written to the database.
*   **Step 2: Sync to Orchestrator DB (`cove`):**
    *   *Mechanism:* Connects to the `cove` database (using connection guards) and upserts prompts into the `public.system_prompts` table with versioning.
    *   *Result:* Ensures the orchestrator running Temporal agent runs always fetches the exact, updated prompt versions dictated by the filesystem.
*   **Step 3: Sync to main DB Graph (`amplified_brain`):**
    *   *Mechanism:* Connects to the AGE graph database and upserts vertices representing the rules/doctrinal files, updating their coordinate properties (file path, hash, epistemic tier, UUID) without storing raw body text.
    *   *Result:* Preserves the **Assertion-Context Boundary**. The database remains a lightweight, sub-millisecond logical index (storing only pointers and metadata), while the filesystem remains the source of truth for raw context.
*   **Step 4: Verification Check (`--verify`):**
    *   *Mechanism:* Pulls current hashes from the databases and compares them against the filesystem, returning exit code `0` on match, or `1` on drift.
    *   *Result:* Provides a zero-overhead way to monitor the integrity of the databases and trigger self-healing resyncs if drift occurs.

### 3. Is this the complete goal or a part of it?
This is a **constituent part** of the complete goal:
*   **The Complete Goal:** A platform-agnostic, local-first data lake where AI agents can consume ingestion files, rules, and prompts with sub-millisecond retrieval.
*   **This Part:** The sync script acts as the **bridge**. While the watcher (`inbox_watcher.py`) handles chunking/local caching, and the search CLI (`search_chunks.py`) handles prompt context assembly (the Logic Sandwich), this pipeline writes the indices/relationships back to the PostgreSQL database on Beast, tying the filesystem and the graph together.

Yes. This is the core architectural insight of **AgentFS**. 

### 1. The File is the Node
Each individual Markdown file (`.md` or `.txt` chunk) is a self-contained, physical database node. 
*   **The Schema:** Enforced by the 19-field Dual-YAML header (defining its identity, coordinates, cryptographic witness, and scopes).
*   **The Payload:** The raw text content.
*   **The Version Control:** Git acts as the database transaction log, giving us rollback history, branch isolation, and diffs for free.

### 2. The Main Database is the Map, Not the Storage
Under this model, `amplified_brain` (Postgres/AGE) is **not** a data store. It is a **cognitive directory/registry**.
*   It organizes the nodes (filesystem files) and maps the relationships (edges) between them.
*   It holds the coordinate system (paths and hashes) to allow fast semantic/graph queries, but it does not house the actual knowledge.
