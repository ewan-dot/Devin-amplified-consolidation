### 3. Why this is mathematically and operationally superior
1.  **100% Data Sovereignty:** An SMB's database is just a folder of files. They can take their "nodes" with them in a zip file. They do not need to manage PostgreSQL, Docker, or AGE to own their data.
2.  **Instant Rebuilds:** If the database server is destroyed, running the sync script (`sync_ledger_to_dbs.py`) scans the folders and completely reconstructs the query index in seconds.
3.  **Local-First AI Ergonomics:** When an AI agent searches, it queries the index to find the coordinates, and then reads the filesystem directly. This keeps database connections lightweight, fast, and secure.

### ASSISTANT (Session 615d6e08)
This is the concept of a **Scale-Free or Fractal Database (AgentFS)**. 

The schema is fractal: the exact same metadata fields describe the unit of data at **every tier of scale**.

```mermaid
graph TD
    Pillar["Tier 2: Pillar / Domain Node (e.g., Billing System) <br> [YAML: Title, UUID, Domain, parent_nodes=[Parent]]"]
    Doc["Tier 1: Document / Process Node (e.g., Billing Rules) <br> [YAML: Title, UUID, parent_nodes=[Pillar_UUID]]"]
    Chunk["Tier 0: Leaf / Slice Node (e.g., Chunk 01 - 300 lines) <br> [YAML: Title, UUID, parent_nodes=[Doc_UUID]]"]
    
    Pillar --> Doc
    Doc --> Chunk
```

### 1. The Fractal Units
Regardless of the volume of data, we need only **17-19 fields** to represent any node at any scale:

1.  **Tier 0 (The Slice):** A raw 300-line text file containing granular facts.
    *   *Described by:* 19 fields (focusing on local coordinates like `chunk_index`, `start_line`, `chunk_hash_sha256`).
2.  **Tier 1 (The Document):** An aggregation of Tier-0 slices (the overall file).
    *   *Described by:* The exact same 19 fields, but the coordinates now encompass the whole (e.g. `total_chunks: N`, `file_hash_sha256` of the entire document). It references the Pillar UUID as its parent.
3.  **Tier 2 (The Pillar/Corpus):** An aggregation of Tier-1 documents (e.g. "All Billing Doctrine").
    *   *Described by:* The exact same 19 fields. Its payload is a manifest of child UUIDs, and it links to the parent domain.

### 2. How the AI Traverses the Fractal
Because the database is structured this way:
*   The AI can read a **Tier 2 (Pillar)** node to understand high-level governance and locate child documents.
*   It hops down to a **Tier 1 (Document)** node to select the specific rule-set.
*   It fetches only the specific **Tier 0 (Slice)** chunks matching its query, pulling only the relevant facts into context.

By keeping the taxonomy identical at every level of aggregation, the AI uses a single, uniform set of retrieval rules to zoom in and out of the entire estate. The file layout itself acts as a clean, hierarchical index.

Exactly. That is the core division of labor in our architecture:

1.  **AI (Probabilistic):** Good at synthesis, pattern matching, and reasoning over context. Bad at strict, zero-tolerance logic constraints.

If we let an LLM handle database sync or hash validation, it would occasionally misread a hash, skip a metadata field, or hallucinate a database path. 

By delegating validation entirely to **Python** inside `sync_ledger_to_dbs.py`, we guarantee that:
*   Every single character of the prompt matches the ledger hash (using cryptographic `hashlib`).
*   No split databases or schema pollution occur (using `db_harness.py`).
*   Database state is 100% mathematically consistent with the filesystem, failing loudly if anything drifts. 

Python enforces the rails; the AI runs within them.
