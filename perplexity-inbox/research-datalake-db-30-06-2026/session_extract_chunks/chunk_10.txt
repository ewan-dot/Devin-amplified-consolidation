- Same input always produces same label
- No human judgment in the loop at the labeling stage
- Errors are uniform, not random
- The system can be improved by changing rules, not by reprocessing individual decisions

### ASSISTANT (Turn 93)
Correct on both counts.

**Model-specific distance is empirically established.** All-MiniLM-L6-v2 (what Beast runs) has a different cosine distance distribution than OpenAI `text-embedding-3-large` or Nomic. A threshold of 0.3 in one space is not 0.3 in another — the geometry is not interchangeable. There is no universal threshold. Every embedding model needs its own calibration curve.

**The mode-dependent dial is the right abstraction:**

```
INVESTIGATE  ←————————————————→  PRODUCTION
  high distance                   low distance
  (loose threshold)               (tight threshold)
  more candidates                 fewer, precise
  diverse recall                  high precision
  misses rare                     misses novel
```

In investigation mode you want the long tail — things that are related but not obvious. In production you want zero noise — the wrong answer is worse than no answer.

**How to build it:**

Per model, run a calibration pass against a held-out evaluation set. Plot precision-recall curves at distance intervals (0.05 steps). This gives you:

- `D_investigate` — the knee where recall starts dropping (accept everything above)
- `D_production` — the knee where precision starts dropping (accept only below)

Store these as model-level config, not hardcoded constants. When the embedding model changes, recalibrate. The pipeline reads mode from context → selects threshold → passes to vector query.

The calibration data comes from your own corpus — which is why the immutable ledger matters. You need a stable dataset to calibrate against. If the dataset moves, the threshold moves, and you don't know which caused what.

### ASSISTANT (Turn 99)
The linking point taxonomy is the graph schema. Each type is a different edge class:

```
LINGUISTIC LINK    — same concept, different vocabulary (jargon translation)
MATHEMATICAL LINK  — isomorphic structure across domains (same shape, different field)
LOGICAL LINK       — same inference pattern, different context (if-then structure match)
DIMENSIONAL LINK   — same axis relationship, different domain (ratio, gradient, threshold)
```

The graph holds all four edge types. The vector holds semantic position. They're complementary — the vector tells you *where* something is, the graph tells you *what it connects to and why*.

The glasses/lens is the rotation operator. When you apply a lens:

- It doesn't change the data
- It reweights which edge types are active
- It rotates the similarity axes so the relevant linking points face upward
- What surfaces at the top is a function of orientation, not just content density

So the same node — say, "iterative refinement" — sits in a fixed position in the database. Mathematical lens → its shape-isomorphism edges activate, Kaizen and gradient descent surface. Linguistic lens → its jargon-translation edges activate, domain-specific synonyms surface. Logical lens → its constraint-pattern edges activate, Bayesian updating and selection pressure surface.

The sphere never moves. The viewer rotates.

The practical architecture: lens is detected from conversation trajectory → passed as a weighting vector to the graph traversal → edge type weights shift → retrieval follows the weighted graph → surfaces what that lens makes visible.

The linking points are the edges. The glasses are the weights. The sphere is the data. The rotation is the query pre-processing step.
